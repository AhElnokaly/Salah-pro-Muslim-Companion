7. لا تبني نظام عام (plugin registry / scheduler عام). الـ runner بيخدم الاختبارين دول فقط.
8. بعد كل خطوة: `tsc` نضيف + `npm test` ناجح. راجع `git status` وامسح ملفات AI Studio الجانبية.

## الجزء 1: Test Runner

ملفات جديدة تحت `src/diagnostics/tests/` (أو الأقرب لهيكل المشروع).

### 1.1 الـ spec

```ts
interface DiagTestSpec {
  id: string;                    // 'fix1a-preview-source'
  title: string;                 // عربي
  fixRef: string;                // 'Fix 1a' | 'B3'
  mode: 'instant' | 'timed';
  touchesKeys: string[];         // [v2] المفاتيح اللي الـ test هيغيرها (أساس الـ snapshot)
  setup: (ctx) => Promise<void>;
  schedule?: (ctx) => Promise<ScheduledEvent[]>; // لازم ترجع المعرّفات اللي اتجدولت فعلاً
  userSteps?: DiagUserStep[];    // خطوات يدوية أو تأكيدات
  collectAt?: number;            // epoch ms، يتحسب بعد نجاح الجدولة
  evaluate: (ctx, log) => Promise<DiagResult>;
}
```

### 1.2 سجل الـ run **[v2]**

يتخزن في مفتاح واحد (`diag_run_state`) ويتحدّث بعد **كل خطوة** (مش في الآخر):

- `runId`, `testId`, `startedAt`
- `phase`: `idle` → `armed` → `waiting` → `collectable` → `reported` (+ `cancelled`)
- `collectAt` (ميعاد جمع النتيجة) و`expiresAt` (آخر ميعاد مسموح) **منفصلين**
- `snapshot`: القيم الأصلية + القيمة اللي الـ test ضبطها لكل مفتاح
- `scheduled`: الأحداث اللي اتحاولت، وكل واحد اتأكدت جدولته ولا لأ
- `cleanup`: `none | started | done | failed`

معنى الحالات:
- `collectable`: وصل `collectAt` ولسه قبل `expiresAt`، والـ setup والجدولة اكتملوا.
- لو عدّى `expiresAt` قبل الجمع: **يتلغى ويتنضف** وتطلع النتيجة `INCONCLUSIVE` بسبب "انتهت المهلة"، ولا يتحول لـ `collectable`.
- `reported`: التقرير اتولّد واتحفظ (مش بالضرورة اتشاف).

عند فتح التطبيق: لو فيه run معلّق، القرار بيعتمد على الحقول دي (مثلاً الـ setup ما اكتملش ← restore فوراً؛ فيه أحداث اتجدولت ← تنظيفها قبل أي حاجة).

### 1.3 سياسة الفشل **[v2]**

- أي فشل في `setup` أو في جدولة أي حدث ← الـ run يتوقف، يتعمل restore + تنظيف، والنتيجة `INCONCLUSIVE` (أو `FAIL` لو السبب واضح إنه الـ fix)، **ممنوع `PASS`**.
- فشل قراءة الـ fire log ← `INCONCLUSIVE`.
- لو الـ restore نفسه فشل: يظهر للمستخدم بوضوح في الـ banner والتقرير (مش بيتخفى).

### 1.4 Snapshot / Restore / Cleanup

- Snapshot لـ `touchesKeys` فقط، قبل أول تغيير.
- **[v2] Compare-and-restore:** يرجّع القيمة الأصلية **بس لو القيمة الحالية لسه هي اللي الـ test ضبطها**. لو أحمد غيّرها يدوياً أثناء الاختبار، ما تتكتبش فوقها، وتتسجل في التقرير.
- Restore idempotent.
- **[v2] تنظيف الـ alarms الاصطناعية:** مطابقة بالـ prefix `diag_` بالظبط فقط، ممنوع أي مطابقة أوسع. بيتنفذ عند: نهاية الـ test، `Cancel`، انتهاء `expiresAt` (عند فتح التطبيق)، وعند boot recovery لو الإضافة ممكنة بأمان. الحذف يتأكد منه بأدق دليل متاح (مش بس نجاح استدعاء الإلغاء)، والتقرير يكتب إيه اللي اتأكد وإيه اللي ما اتأكدش.
- مفيش watchdog native جديد في Phase 1.

### 1.5 UI

داخل شاشة تقرير التشخيص، قسم "اختبارات الإصلاحات":
- قائمة الـ tests: العنوان + `fixRef` + زر `Run test`.
- أثناء الـ run: banner أحمر ثابت "وضع الاختبار شغال" + العداد + زر إلغاء، مبني على الحالة المحفوظة (مش على React state).
- رسالة واضحة بميعاد الرجوع، وlocal notification لو متاح بدون ما يأثر على الأذان. لو الإشعار ما اتجدولش، التطبيق يقول ده صراحة.
- لو فيه صلاة حقيقية خلال 10 دقايق: تحذير (معلومة للمستخدم، مش حماية؛ الحماية إن الـ tests ما بتلمسش الحقيقي).

### 1.6 التقرير **[v2]**

زر `نسخ التقرير` + `مشاركة`، نص `.md`:

```
# Diag report: <testId> (<fixRef>)
- runId / start / collect time / app version / device / Android version
- battery optimization / exact alarm / DND access status (مع وقت القياس)
## Repo findings (أول مرة فقط)
## Settings snapshot (الأصلي ← اللي الـ test ضبطه ← الحالي عند الجمع)
## Expected vs Actual (جدول؛ أي قيمة ما اتقاستش تتكتب "لم يُقَس")
## Events (من الـ fire log، مربوطة بـ runId/alarmId)
## Result: PASS | FAIL | INCONCLUSIVE + سبب محدد بجملة
```

بدون بيانات شخصية.

## الجزء 2: الاختبارين

### Test A: `fix1a-preview-source` (mode: `instant`، مع توقف لتأكيد المستخدم)

التدفق:
1. قياس مؤذن محمّل + مؤذن غير محمّل (online).
2. توقف: "اقفل الواي فاي والداتا ثم اضغط متابعة".
3. إعادة القياس.
4. تقييم.

- يستعمل `resolvePreviewSource` و`getAudioUrl` الحقيقيين، ولا يشغل صوت.
- Expected: محمّل ← `local` حتى offline. غير محمّل offline ← `default`. غير محمّل online ← `remote`.
- `navigator.onLine` يتسجل كـ "مؤشر اتصال من المتصفح" مش دليل وصول للإنترنت. لو أحمد ما أكدش إنه قفل الاتصال، الحالة offline تتسجل `لم يُقَس`.
- **[v2]** لو `getAudioUrl` بيحمّل أو يكتب cache كأثر جانبي، الـ test يستخدم مسار قراءة فقط أو يسجل الأثر ويرجّعه. ولو مفيش طريقة، يتبلّغ.
- التقرير يوضح إن الـ test يثبت **اختيار المصدر** وليس نجاح التشغيل.

### Test B: `b3-khushu-custom-alarm` (mode: `timed`)

**[v2] الترتيب مهم:** Khushu بيكتم الجهاز لفترة، فالـ control لازم **قبله**.

1. Alarm 1 (control): بعد 3 دقايق، نفس الصوت، **بدون Khushu**.
2. Alarm 2: بعد 6 دقايق، نفس الصوت، **مع Khushu**.
3. قبل كل alarm: سجّل ringer mode/DND الحالي. وبعد آخر حدث: سجّل الحالة تاني.
4. `collectAt` = وقت انتهاء Khushu المتوقع (من الكود، سؤال 6) + 3 دقايق.
5. خلال الفترة دي أحمد مش بيشغّل صوت تاني على الجهاز ولا يغيّر الـ DND يدوياً (الـ banner يذكّره).

التسجيل (native، تسجيل فقط، مربوط بـ `runId` و`alarmId`):
- `audio_started` (إشارة فعلية من المشغل، مش طلب التشغيل)
- `audio_completed` (انتهاء طبيعي)
- `audio_error` (مع السبب المتاح)
- لو الإشارات الموجودة أصلاً مكافئة، استخدمها بدل إضافة جديدة.

التقييم:
- `PASS` فقط لو: Alarm 1 فيه `audio_started` + `audio_completed`، وAlarm 2 فيه `audio_completed` ثم `khushu_activated` بالترتيب الزمني، **وأحمد أكّد سماع الصوت** (زرار نعم/لا في التقرير). لو التأكيد ما حصلش ← الحالة "التشغيل البرمجي اكتمل، السماع لم يُتحقق منه" وليس `PASS` كاملاً.
- لو Alarm 1 ما اتجدولش أو الـ control ما اشتغلش ← `INCONCLUSIVE` (مفيش مقارنة).
- لو ringer/DND كانت في حالة مختلفة عن المتوقعة قبل Alarm 2 بسبب غير Khushu ← `INCONCLUSIVE`.
- غياب حدث متوقع من log اتجمع متأخر أو ناقص ≠ دليل فشل؛ يتصنف `INCONCLUSIVE` مع السبب.
- الـ test **ممكن يفشل**، وده المقصود. ممنوع إصلاح B3 هنا.

## Definition of Done

1. `tsc` نضيف و`npm test` ناجح.
2. Unit tests للـ runner (على الأقل 4): kill بعد الـ snapshot وقبل اكتمال `setup`، kill بعد جدولة حدث اصطناعي، restore مرتين، compare-and-restore لما المستخدم يغير القيمة.
3. الـ dev flag مقفول افتراضياً.
4. `git status` فيه الملفات المقصودة فقط.
5. آخر الرد: اللي اتعمل، اللي مش متأكد منه، **وخطوات اختبار على الجهاز لأحمد** (بالترتيب، واحدة واحدة): تشغيل Test A، تشغيل Test B، kill التطبيق في نص run، reboot في نص run والتأكد إن الـ alarms الاصطناعية اتنضفت والأذان الحقيقي سليم. اختبارات الوحدة لا تثبت سلوك Android الحقيقي، والتقرير النهائي يذكر ده.
